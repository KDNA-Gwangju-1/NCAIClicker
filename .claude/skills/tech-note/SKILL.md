# 기술 문서 쓰기

1. `docs/TECH_NOTES/README.md` 를 읽는다. 규칙 원문은 거기에만 있다.
2. **해당 기능의 문서가 이미 있는지 먼저 찾는다.** 있으면 새로 만들지 말고 그 문서를 고치고
   맨 아래 **갱신 이력**에 한 줄 추가한다. 이슈마다 새 문서를 만들지 않는다.
3. 실제 소스를 읽어 클래스·경로·이벤트·CSV 열을 **코드에서 확인한다.** 기억이나 계획서로 쓰지 않는다.
4. 새로 만들 때만 `_TEMPLATE.md` 를 복사해 `docs/TECH_NOTES/<기능-이름>.md` 로 만든다.
   **파일명은 기능 이름이다. 이슈 번호를 넣지 않는다** — 문서는 이슈보다 오래 산다.
5. 도식은 **문서 안에 Mermaid 코드블록**으로 넣는다. GitHub이 PR 화면에서 바로 렌더한다.
   - C4 **L3 Component** 수준으로 그린다 — `flowchart` 에 `subgraph` 로 모듈 경계를 준다.
     (GitHub의 Mermaid는 C4 전용 문법을 렌더하지 못한다.)
   - `GameEvents` 를 거치는 관계는 이벤트 노드를 경유해 그린다. 모듈끼리 직접 잇지 않는다.
   - 렌더된 png/svg 는 만들지도, 커밋하지도 않는다.
6. **"왜 이 방법인가" 표의 버린 방법과 이유를 비워 두지 않는다.** 모르면 지어내지 말고
   작업자에게 묻는다 — 이 칸이 비면 문서를 쓴 의미가 없다.
7. "검증" 절에는 **실제로 실행해 확인한 것만** 적는다. 안 했으면 "미검증"이라고 적는다.

이 파일과 `docs/TECH_NOTES/README.md` 의 내용이 다르면 README 를 따른다.
