# 문서 ↔ 프로젝트 대조 검증

겉보기에 기능이 돌아가고 문서도 트집 잡을 게 없는데 의심스러울 때 쓴다.
**기술 문서와 실제 코드가 어긋나 있으면 어딘가 틀어진 것이다.**

1. 의심되는 기능의 `docs/TECH_NOTES/*.md` 를 찾아 읽는다. 문서가 없으면 그 사실부터 보고한다
   — 대조할 기준이 없다는 뜻이다.
2. 문서에 적힌 것과 **실제 코드를 하나씩 대조한다.** 기억이나 추론으로 채우지 않고 파일을 연다.

   | 문서의 항목 | 확인 방법 |
   |---|---|
   | 클래스 목록과 경로 | 그 경로에 그 파일이 실제로 있나. 문서에 없는 클래스가 늘어나 있나 |
   | 구독·발행 이벤트 | 코드의 `GameEvents` 구독/발행이 문서와 같나. `OnEnable`/`OnDisable` 쌍은 맞나 |
   | 읽는 CSV 열 | 그 열이 CSV에 실제로 있나. 코드가 다른 열을 읽고 있지 않나 |
   | 도식의 관계 | 도식에 없는 참조가 코드에 생겼나. 도식의 화살표가 실제와 반대는 아닌가 |
   | 알려진 한계 | 이미 해결된 것이 한계로 남아 있나 (문서가 낡음) |

3. 어긋난 곳마다 **문서가 낡은 것인지 코드가 잘못된 것인지**를 구분해 보고한다.
   확신이 서지 않으면 "판단 필요"로 남긴다. 임의로 고치지 않는다.
4. 문서가 아예 없거나 내용이 비어 있으면, 그 자체를 **가장 큰 위험**으로 보고한다.

## 보고 형식

```
### 어긋난 곳
| 항목 | 문서 | 실제 코드 | 어느 쪽이 틀렸나 |
|---|---|---|---|

### 문서에 없는 것 (코드에만 있음)
-

### 코드에 없는 것 (문서에만 있음)
-

### 대조한 항목
- 확인한 문서와 항목을 전부 적는다. 확인하지 못한 것은 "미확인"이라고 적는다
```

**이걸로도 안 잡히면** 다른 모델로 같은 대조를 한 번 더 돌리라고 사용자에게 권한다.
