# Git 작업 흐름

브랜치·커밋·PR 규칙의 **정본**이다. 다른 문서는 이 파일을 가리키기만 하고 내용을 옮겨 적지 않는다.

## 1. 브랜치 구조

```
main        배포 가능한 상태만. 직접 커밋하지 않는다
 └ Develop  통합 브랜치. 모든 기능이 여기로 모인다
    └ feature/...   한 작업 = 한 브랜치
```

- **`main` 에 직접 커밋하지 않는다.** `Develop` → `main` 도 PR로만 한다.
- **`feature/*` 의 PR 대상은 `Develop` 이다.** `main` 이 아니다.
- 저장소에 `Develop` 이 이미 있다. 착수 전 `git checkout Develop && git pull` 로 시작한다.

### 브랜치 이름

```
feature/<이니셜>-<모듈>-<이슈번호>-<계획번호>-<설명>
```

| 조각 | 뜻 | 예 |
|---|---|---|
| 이니셜 | 작업자 영문 이니셜 대문자 | `KSH` |
| 모듈 | 담당 영역 | `economy`, `core`, `ui`, `fever`, `save` |
| 이슈번호 | GitHub 이슈 번호 | `12` |
| 계획번호 | EXECUTION_PLAN 항목 번호의 점을 `_` 로 바꾼 것 | `3_2_1` (3.2.1), `1_11` (1.11) |
| 설명 | 영문 소문자 케밥 | `upgrade-cost` |

예: `feature/KSH-economy-12-3_2_1-upgrade-cost`

**구분자는 하이픈이다.** 슬래시로 나누지 않는다 — `feature/KSH` 가 디렉터리이자 브랜치가
되려 해서 git이 거부하는 경우가 생긴다.

**계획번호의 점을 `_` 로 바꾸는 이유**: 브랜치명에 `.` 이 들어가면 `1.2.1` 같은 태그·참조와
섞여 읽히고, `..` 이나 끝의 `.lock` 은 git이 아예 거부한다. 그렇다고 점을 **빼서는 안 된다** —
조각이 두 자릿수가 되는 순간 경계를 잃는다. `1.11.1` 과 `1.1.11` 이 둘 다 `1111` 이 되어
구별되지 않는다. 그래서 점을 지우지 말고 `_` 로 **치환한다**: `3_2_1`, `1_11`.
계획에 대응하는 항목이 없는 작업(핫픽스성 잡일 등)은 이 조각을 생략한다.

**이니셜을 앞에 두는 이유**: 5명이 동시에 브랜치를 파면 `git branch -a` 목록에서 누구 것인지
한눈에 안 보인다. 이름 하나로 담당자를 묻는 대화가 사라진다.

배포 후 긴급 수정만 예외로 `main` 에서 딴다: `hotfix/<이니셜>-<설명>`.
이 경우 **`main` 과 `Develop` 양쪽에 반영**해야 한다. 한쪽만 고치면 다음 릴리스에서 버그가 되살아난다.

### 이슈가 없는 브랜치

```
chore/<이니셜>-<설명>
```

**원칙은 이슈가 먼저다.** 이슈가 작업 지시서이고 완료 기준의 정본이므로(3절), 일이 있으면
이슈를 세우는 것이 기본이다. 아래 셋만 예외로 이슈 없이 딴다.

| 쓰는 경우 | 예 |
|---|---|
| 오탈자·깨진 링크 등 판단이 필요 없는 문서 수정 | `chore/KSH-fix-typo-in-gdd` |
| 빌드·CI가 깨져 지금 멈춰 있는 것을 되돌리는 응급 수정 | `chore/KSH-revert-broken-importer` |
| 개인 실험 — **PR을 올리지 않는다** | `chore/KSH-spike-object-pool` |

**판단이 들어가면 예외가 아니다.** 수치를 바꾸거나 공용 계약을 건드리거나 "이렇게 하는 게
맞나"를 묻게 되면 멈추고 이슈를 세운다. 이슈 없이 머지된 변경은 **왜 그렇게 했는지 물어볼
곳이 없다** — 커밋 메시지는 무엇을 했는지만 남기고 무엇을 하지 않기로 했는지는 남기지 않는다.

`feature/` 를 쓰지 않는 이유: 접두어만 보고 "이건 계획에 있는 작업인가"를 가를 수 있어야
한다. 이슈 없는 것까지 `feature/` 로 들어오면 그 구분이 사라지고, 이슈번호가 빠진 이름을
봐도 원래 없는 것인지 빠뜨린 것인지 알 수 없다.

### 브랜치 수명

- 하루를 넘기지 않는다. 길어지면 충돌이 커진다.
- 커밋 3회 또는 30분마다, 그리고 PR 직전에 `git fetch origin Develop && git rebase origin/Develop`.
- 리베이스 중 공용 인터페이스·이벤트·CSV 스키마가 바뀐 것을 발견하면 **두 버전을 섞지 말고
  멈춘 뒤 해당 이슈에 코멘트로 보고한다.**
- PR이 머지되면 브랜치를 삭제한다. 남겨두면 다음 사람이 어느 게 살아 있는지 모른다.

## 2. 커밋

### 메시지 형식

**Conventional Commits 접두어 + 한국어 요약.** 접두어는 아래 6개만 쓴다.

| 접두어 | 쓰는 경우 | 예시 |
|---|---|---|
| `feat` | 기능 추가 | `feat: 호버 자동 타격 추가` |
| `fix` | 버그 수정 | `fix: 코인이 두 배로 들어오던 문제 수정` |
| `refactor` | 동작은 그대로 두고 코드 정리 | `refactor: 타격 판정을 FSM으로 분리` |
| `docs` | 문서만 변경 | `docs: 밸런스 근거 보강` |
| `chore` | 설정·에셋·빌드 등 그 외 | `chore: 망치 프리팹 추가` |
| `ci` | 워크플로·대시보드 | `ci: 대시보드 갱신 주기 조정` |

요약은 50자 이내, 마침표 없이. 이유가 필요하면 본문에 적는다.

### 무엇을 담나

- **한 커밋에 한 가지 일만.** `git add -A` 로 훑어 담지 말고 파일 단위로 스테이징한 뒤
  `git diff --cached --stat` 으로 확인한다 — 작업 중 흩어진 파일이 무관한 커밋에 딸려 들어간다.
- CSV를 고쳤으면 재임포트한 `BalanceData.asset` 을 **같은 커밋에** 담는다. 따로 커밋하면
  중간 커밋에서 데이터와 에셋이 어긋난다.
- `.meta` 는 원본 파일과 **같은 커밋에** 담는다. 따로 올리면 다른 사람 쪽에서 참조가 끊긴다.
- 커밋해 놓고 push 하지 않은 채 퇴근하지 않는다. 그 작업은 팀에게 존재하지 않는 것과 같다.
- **새로 만드는 파일·폴더 이름은 ASCII만.** 팀에 macOS 사용자가 있어 한글 파일명은
  NFD/NFC 차이로 git이 다른 파일로 인식한다 (`AGENTS.md` "명명"). 커밋 메시지·문서 내용은 한국어 그대로 쓴다.
- `core.quotepath` 를 `false` 로 두면 git 출력에서 한국어가 깨지지 않는다 (PC마다 1회):
  `git config --global core.quotepath false`

## 3. 이슈

**이슈가 작업 지시서다.** 완료 기준의 정본은 이슈 본문이고, 코드나 대화가 아니다.

- 착수 전 담당자·상태를 확인한다. 비어 있으면 자신을 배정하고 **즉시** In Progress로 바꾼다.
  확인과 상태 변경 사이가 벌어지면 두 사람이 같은 이슈를 집는다.
- 상태는 **Todo / In Progress / Done** 셋만 쓴다. 진행률을 추측하지 않는다.
- 막힌 작업은 컬럼을 옮기지 말고 **`blocked` 라벨**을 붙인다. 컬럼으로 빼면 누가 어디까지
  들고 있었는지가 사라진다 — 라벨이면 어느 컬럼에 있든 보인다.
- 공용 계약(인터페이스·이벤트·CSV 스키마)을 바꿔야 하면 **구현 전에 이슈를 먼저 발의한다.**
- 작업 번호(`2.3`, `4.1`)는 이슈와 1:1로 대응한다.
- **번호가 겹치면 이슈 번호가 앞선 쪽을 원본으로 두고, 뒤쪽 이슈 제목의 번호를 빈 번호로 옮긴다.**
  대시보드와 `/list-work` 가 번호로 카드를 찾으므로 겹친 채로 두면 선행 판정이 흔들린다.
  앞선 쪽을 원본으로 삼는 것은 먼저 만든 이슈를 이미 다른 곳에서 그 번호로 부르고 있기 때문이다.
  둘 다 판정에서 빠지지는 않는다 — 겹친 동안에는 양쪽 다 `정정 필요` 로 보고된다.

### 선행 줄 — 형식을 지킨다 (기계가 읽는다)

이슈 본문의 아래 한 줄을 **[진행 현황 대시보드](https://kdna-gwangju-1.github.io/NCAIClicker/)가
파싱해서** "지금 착수 가능 / 대기 중"을 자동으로 계산한다. 사람이 라벨을 붙이거나 카드를
옮길 필요가 없는 대신, **형식이 틀리면 판정이 틀린다.**

```
**선행**: 없음
**선행**: 1.2.1
**선행**: 1.3.2, 2.3
**선행**: 3.x          ← 3번 묶음의 모든 카드
**선행**: 2.2~2.5      ← 같은 묶음의 연속 번호 (해당 카드 전부 존재해야 함)
**선행**: #12          ← 이슈 번호로도 된다
```

| 쓸 때 | 결과 |
|---|---|
| 형식대로 적음 | 선행이 전부 닫히면 **자동으로 "착수 가능"에 올라온다** |
| 줄이 아예 없음 | **"선행 확인 필요"** 칸에 빨갛게 뜬다 (착수 가능으로 잘못 올라오지 않는다) |
| 오타·빈 값·미존재 #이슈·빈 묶음·잘못된 범위 | 선행 확인 필요로 분류한다. 일부 토큰만 읽고 나머지를 버리지 않는다 |
| 아직 보드에 없는 명시적 작업 번호 | 완료로 보지 않고 대기 중으로 분류한다 |

- **줄을 지우지 말고 `**선행**: 없음` 이라고 적는다.** 지우면 확인 필요로 분류된다.
- 이슈를 새로 만들 때는 `작업` 템플릿을 쓰면 이 줄이 이미 들어 있다.
- 선행을 바꿨으면 [EXECUTION_PLAN.md](EXECUTION_PLAN.md) 표의 **선행** 열도 같이 고친다 —
  두 곳에 있는 유일한 값이라 어긋나면 사람과 기계가 다른 순서로 일하게 된다.

## 4. PR

- **대상 브랜치는 `Develop`.**
- 제목은 커밋과 같은 형식. 본문은 [`PULL_REQUEST_TEMPLATE.md`](../.github/PULL_REQUEST_TEMPLATE.md) 를 따른다.
- **검증 결과를 반드시 적는다.** Edit Mode / Play Mode에서 실제로 확인한 것만 적고,
  안 했으면 "미검증"이라고 적는다. 지어내지 않는다.
- 구현 PR이면 [`docs/TECH_NOTES/`](TECH_NOTES/) 문서를 **같은 PR에** 담는다.
- **리뷰는 올리는 사람이 직접 한다.** 타인에게 요청하지 않는다 — 5명이 7일 안에 서로를
  기다리면 그 대기가 일정을 잡아먹는다. 대신 올리기 전에 `convention-checker` 로 규칙을
  점검하고, PR 본문의 검증 결과에 **실제로 확인한 것만** 적는다.
  (교차 검증이 빠지는 만큼 자기 PR 의 diff 를 한 번은 끝까지 읽고 올린다.)
- 머지 전략은 **Squash and merge** 로 통일한다.
- **머지는 사람이 한다.** 에이전트는 PR 생성까지만 한다.

## 5. 이슈 하나를 닫는 절차

1. 구현 → 사람이 검수
2. `convention-checker` 로 공용 계약 점검
3. 기술 문서 작성 ([`docs/TECH_NOTES/`](TECH_NOTES/))
4. PR 생성 (이슈 상태는 In Progress 그대로)
5. 본인이 확인 → Squash merge → 브랜치 삭제
6. 이슈 Close → 상태 Done

**2~3번을 건너뛰지 않는다.** 검수를 한두 번 놓치기 시작하면, 컨벤션은 맞는데 어떤 논리로
만들었는지 아무도 모르는 코드가 쌓인다. 그때부터는 수정·버그픽스의 작업 일정을 말할 수 없게 된다.
