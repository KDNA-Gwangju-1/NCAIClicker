# 밸런스 설계표

모든 수치는 `Assets/GameData/Balance/*.csv`가 원본이다. 이 문서는 **왜 그 숫자가 됐는지**를 적는다. 숫자를 바꿀 때는 CSV를 고치고, 근거가 달라졌으면 이 문서도 같이 고친다.

## 1. CSV를 원본으로 삼는 이유

Unity에서 밸런스 데이터를 다루는 방법은 보통 ScriptableObject(이하 SO)다. 그런데 SO 에셋(`.asset`)은 YAML이라 **여러 명이 같은 파일을 고치면 Git 충돌이 나고, 충돌 해결이 어렵다.** [EXECUTION_PLAN.md](EXECUTION_PLAN.md)에서 공유 SO의 동시 수정을 위험으로 지목한다.

CSV를 원본으로 두면 이 문제가 사라진다.

| | CSV 원본 | SO 직접 편집 |
|---|---|---|
| Git 충돌 | 행 단위 자동 병합 — 다른 행을 고치면 충돌 없음 | 파일 전체 충돌, 수동 해결 |
| 편집 도구 | Excel, Google Sheets, 메모장 | Unity 에디터를 켜야 함 |
| 리뷰 | PR diff에 `40 → 25`로 보임 | YAML 덩어리라 판독 어려움 |
| 타입 안전성 | 없음 (임포트 시 검증 필요) | 있음 |

**구조**: CSV는 원본, SO는 빌드 산출물이다.

```
Assets/GameData/Balance/*.csv   ← 사람이 고치는 원본 (PM이 Unity 없이도 수정 가능)
        ↓ 에디터 임포터 (Unity 에디터에서만 실행)
Assets/GameData/Generated/*.asset  ← 자동 생성 SO
        ↓ 런타임은 이것만 읽는다
```

런타임에서 CSV를 파싱하지 않는 것이 핵심이다. 빌드에 파서를 넣으면 문자열 파싱 실패가 그대로 런타임 크래시가 된다. 임포트는 에디터에서 끝내고, 실패하면 그 자리에서 콘솔 에러로 잡는다.

**규칙**: 생성된 SO는 손으로 고치지 않는다. 고쳐도 다음 임포트에 덮어써진다.

### 생성된 SO도 저장소에 커밋한다

산출물인데 왜 커밋하느냐 하면, **프리팹과 씬이 이 에셋을 GUID로 참조하기 때문**이다. 각자 로컬에서 생성하게 두면 사람마다 GUID가 달라져서, 내 PC에서 연결한 참조가 남의 PC에서 끊긴다.

임포터는 기존 에셋이 있으면 그것을 갱신하고 새로 만들지 않으므로 GUID는 한번 정해진 뒤 바뀌지 않는다 (현재 `148d52a3...`).

**병합 충돌이 나면 해결하지 말고 재임포트한다.** 생성물이므로 CSV만 맞으면 결과는 같다.

## 2. 스태미나 — 기본 길이와 회복 연장을 구분한다

기본 길이는 `max_stamina / idle_drain_per_sec`로 정하고, 회복형과 퍼크가 이를 늘린다.
**목표 길이는 원작을 따른다** — 아래 "원작 기준으로 재조정" 항목을 먼저 읽는다. 커서 이동·타격 추가 소모는 0, 피버 감소 계수는 1로 고정한다.
이 호환 필드에 다른 값을 넣으면 임포터가 거부한다.

호버 스윙 간격은 `economy.csv`의 `hover_swing_interval_sec`가 원본이다. 런 전체 스윙과 적중 수를
혼동하지 않는다. 예상 적중 수는 `기본 런 길이 / 스윙 간격 × 조준 성공률`이다.

### 원작 기준으로 재조정 (2026-09-18, #34)

`idle_drain_per_sec` 를 **1.6 에서 7.0 으로 올렸다.** 기본 런은 `120 / 7 = 17.1초`다.

**바꾼 이유**: 원작 상점의 **기본 망치 툴팁**에 `스태미나 소모 7/초` 로 적혀 있다 (등급 A, 직접 관찰).
이전 값 1.6 은 자체 시연 목표(60~90초)에서 역산한 것이라 원작 관찰값이 아니었다 —
`max_stamina` 주석이 "원작 최초 기본 최대치로 확인된 값은 아니다"라고 적어 둔 것과 같은 사정이다.

> **6.5 로 잘못 넣었던 적이 있다.** 원작 스크린샷의 6.5 는 `악력` 스킬(초당 소모 -0.5, $110)을
> 찍은 **뒤의** 값이다. 업그레이드된 수치를 기본값으로 넣으면 스태미나 축 업그레이드의 효과가
> 이미 반영된 상태에서 시작하게 된다. **툴팁 수치를 옮길 때는 그것이 기본값인지 강화값인지 본다.**

**짧은 런이 왜 원작의 선택인가**: 이 게임의 긴장은 "마감까지 며칠 남았고 오늘 얼마를 벌었나"에서
온다. 한 런이 75초면 하루가 길어 마감 압박이 옅어지고, 고지서 한 장을 넘기는 데 드는 실제
플레이 시간이 늘어 반복이 지루해진다. 18.5초는 한 번의 실수가 그날을 통째로 망치는 길이다.

**연쇄 영향 — 아직 다시 계산하지 않았다**:

- 아래 "런 길이 검증"과 3절 수입 계산은 **모두 1.6 기준이라 지금은 맞지 않는다.**
  런당 스윙 수가 약 1/4 로 줄었으므로 런당 수입도 그만큼 줄었다고 보아야 한다.
- `stages.csv` 의 목표 코인과 `bills.csv` 의 고지서 금액·기한을 이 길이에 맞춰 다시 뽑아야 한다.
  다시 뽑기 전까지 **첫 고지서 납부 가능 여부는 검증되지 않은 상태다.**
- 재계산은 `.github/scripts/simulate_balance.py` 로 한다 (3절 참조).

### 런 길이 검증 (2026-09-21, #176) — `idle_drain_per_sec` 7.0 기준

`idle_drain_per_sec` 7.0 기준에서 조준 성공률을 바꿔가며 런 길이를 실측했다. 각 2,000회, `--policy random`.
기본 길이는 `120 / 7.0 = 17.14초`이며, 회복형 파괴가 얹혀 실제 런은 17.85초 수준으로 수렴한다.

| 조준 성공률 | 0.3 | 0.5 | 0.6 | 0.8 | 1.0 |
|---|---:|---:|---:|---:|---:|
| 평균 런(초) | 17.85 | 17.85 | 17.85 | 17.85 | 17.85 |
| 평균 회복형 파괴(회) | 0.01 | 0.12 | 0.21 | 0.32 | 0.44 |

짧은 런 길이(약 17.8초)로 원작의 압박감과 짧은 루프 템포를 만족한다.
회복형 저금통의 파괴 빈도는 성공률 0.6 기준 평균 0.21회로, 기본 런을 과도하게 늘리지 않으면서도
의도적인 회복형 타격 시 런을 미세 연장하는 플레이 동기를 부여한다.

수입 쪽 결과는 3절에 있다. 여기서는 길이만 본다.

퍼크 회복량은 이 카드에서 정하지 않았다. 퍼크를 실제로 쓰는 쪽이 작업 4.2 이므로
값만 먼저 두면 읽는 곳 없는 필드가 된다. `stamina.csv` 에 퍼크 항목을 두지 않은 것은 그 이유다.

## 2-1. 단계 목표는 고지서 금액 하나다

예전에는 `stages.csv` 에 `goal_coin` 과 `bill_amount` 가 따로 있었고 **세 단계 모두 같은 숫자**였다

## 3. 경제 — 파괴 모델로 다시 계산한다

**이전 타격당 코인 모델의 총수입·첫 런 돌파 결론은 폐기했다.** 파괴 보상, 회복형, 동시 출현 수,
재등장 대기, 피버를 함께 모델링해야 한다. 새 도구는 `.github/scripts/simulate_balance.py`다.

```bash
python -B .github/scripts/simulate_balance.py --runs 2000 --seed 46 --uptime 0.6 --policy random
python -B .github/scripts/simulate_balance.py --runs 2000 --seed 46 --uptime 0.6 --policy value
```

### 가정과 재현 범위

- 첫 단계, 업그레이드 없음, 대출 없음. 초기 자동 망치가 0이 아니면 도구는 지원하지 않는 조건으로 중단한다.
- CSV 출현 비율로 대상을 뽑는다. 선택한 대상은 파괴까지 유지한다.
- 스윙마다 독립적인 조준 성공 확률을 적용한다. 실제 이동속도·화면 배치·커서 이동 거리는 모델링하지 않는다.
- `random`은 다음 목표를 무작위로, `value`는 보상/내구도가 높은 목표부터 선택한다.
- 적중 시 피버를 채우고 파괴 시점의 피버 배율을 적용한다. 회복은 최대 스태미나까지 제한한다.
- 이 계산은 **몬테카를로 추정이며 Play Mode 실측이 아니다.** 이동 구현과 피버 발동 처리 순서가 정해지면 실제 로그와 비교한다.

### 스폰 모델 (2026-09-21, #156 B안) — 슬롯 타이머를 폐기했다

원작 재관찰(`docs/REFERENCE_ANALYSIS.md` 9절) 결과, "부서진 자리가 고정 시간 뒤 자동으로
채워진다"는 이전 모델은 원작과 다르다는 것이 확인되어 **전면 폐기**했다. 새 모델:

- 부서진 자리는 **자동으로 채워지지 않는다.** `economy.csv`의 `spawn_interval_sec`은
  미사용 호환 필드로 0에 고정했다 (되돌릴 경우를 대비해 필드만 남긴다).
- 파괴할 때마다 `extra_spawn_chance_on_destroy`(기본 0%) 확률로 **즉시 1개가 추가 스폰**된다.
  이 확률은 "저금통 수집벽" 업그레이드가 레벨당 +2%p 올린다(6절 표).
- 책상 위 저금통이 **전부 파괴되면(0마리) 즉시 1개만** 다시 채워진다. 원작 인용:
  *"I do like how when you break all pigs on the table, one will immediately spawn."*
  (`sYyTekFrgvc` 1:18:39)

### 스태미나 7.0 세팅 조정 결과 (2026-09-21, #176)

스태미나 소모 7.0(런 약 17.85초) 환경에서 첫 런의 수입을 실측하고, 1단계 고지서 금액을 중앙값 부근(10 코인)으로 재조정했다.
후속 단계(2단계 25, 3단계 65)는 약 2.5배 성장률로 산출한 초기값이다.

| 모델 | 평균 런(초) | 평균 순수입 | 중앙값 | 수입 10~90 백분위 | 목표 도달 비율 |
|---|---:|---:|---:|---:|---:|
| random | 17.85 | 9.75 | 8.00 | 2.00~29.20 | 37.0% |
| value | 17.85 | 16.44 | 16.00 | 0.00~29.20 | 71.0% |

각 모델은 같은 시드로 2,000회 실행했다. 이 표는 계산 결과 스냅샷이고 **설정값의 정본은 CSV**다.
첫 단계 고지서(10 코인, 기한 5일)는 첫날 무작위 타격 시 37% 확률로 달성하며, 가치 타격 시 71% 확률로 당일 달성한다.
5일 기한 동안 저축하면 무난히 완납할 수 있고, 매일 업그레이드에 전액 탕진하면 마감에 파산하는 긴장감을 유지한다.

### 스폰 모델 교체 후 재검증 (2026-09-21, #156 B안)

슬롯 타이머 모델을 폐기하고 위 "전멸 시 1개 + 확률 기반 추가 생성" 모델로 바꾼 뒤 같은 조건(시드 46, 2,000회)으로 다시 돌렸다.

| 모델 | 평균 런(초) | 평균 순수입 | 중앙값 | 목표 도달 비율 |
|---|---:|---:|---:|---:|
| random | 17.85 | 9.77 | 8.00 | 38.1% |
| value | 17.85 | 16.06 | 16.00 | 70.2% |

**바로 위 표와 사실상 같다.** 업그레이드 없는 1단계 기준에서는 두 모델의 차이가 거의 드러나지
않는데, 기본 런이 17.85초로 짧고 평균 파괴 수가 2회 안팎이라 6마리 동시 출현 중 **책상이
완전히 비는 상황 자체가 드물기 때문**이다 — "전멸 시 1개" 규칙이 발동할 기회가 별로 없다.
그래서 **`stages.csv`의 `bill_amount`는 이번엔 바꾸지 않는다.** 확률 기반 추가 생성이 실제로
체감되는 지점은 저금통 수집벽 업그레이드를 여러 레벨 산 이후이므로, 그 차이는 작업 7.2(3단계
밸런싱 실측)에서 업그레이드 누적 상태로 다시 재본다.

### 경제 기준값 확정 (2026-09-21, #176)

`economy.csv`·`upgrades.csv`의 현재 값을 1단계 출발점으로 확정했다.

- **첫 런 수입으로 업그레이드 4종 중 2~4개를 한 번씩 살 수 있어야 한다.** 첫 런 평균 수입(9.75~16.44 코인)에
  맞춰 4종 초기 비용을 완력 단련 2, 카페인 중독 3, 헬스장 회원권 4, 저금통 수집벽 5(합계 14 코인)로 조정했다.
  첫 결과 화면에서 살 게 없으면 다음 런 동기가 없다.
- **원작 명칭 정리**: 원작의 `악력`은 초당 스태미나 소모 감소 축이다. 우리 프로젝트의 타격 강화 업그레이드는
  원작과의 혼동을 막기 위해 **`완력 단련`**으로 개칭했다. 원작의 `악력`은 향후 스태미나 소모 감소 업그레이드 축으로 남겨둔다.
- **코인 액면 도입 분리**: 코인 액면 도입은 별도 이슈 #178(3.9)에서 진행한다. 3.8 재계산은 현재의 기본 코인 모델을 기준으로 수치를 정립했다.
- **자동 망치 1기는 호버 타격보다 훨씬 약하다.** 호버는 스윙 간격과 조준 성공률(모델 0.6)로,
  자동 망치는 `auto_hammer_power × auto_hammer_hits_per_sec`로 초당 내구도 기여를 계산하면 1기가
  호버의 1/6~1/7이다. 7기 이상은 돼야 호버와 맞먹는다 — 액티브 게임이므로 이 순서를 뒤집지 않는다.
- **초기 자동 망치는 0이다.** 모델이 0을 전제하고, 자동 수입이 있으면 첫 런의 스태미나 압박이 사라진다.
- **비용 성장률은 4종 공통이며 `upgrades.csv`의 `cost_growth`는 0으로 두어 `economy.csv` 값을 따른다.**
  종류별로 다르게 할 이유가 생기기 전까지 한 곳에서만 조정한다.
- **전 업그레이드 만렙 누적 비용은 3단계 목표 합보다 훨씬 크다.** 최대 레벨은 도달 목표가 아니라 상한이다.

### 코인 액면 추첨 (이슈 #178, 잠정)

파괴 보상은 더 이상 단일 값이 아니다. `targets.csv`의 `coin_count`개를 `coins.csv` 가중치 테이블에서
추첨하고, 그 액면들의 합이 지급 금액이다. 액면·가중치의 정본은 `coins.csv`다 — 현재 5종(c1·c5·c25·
c100·c1000)이 등록되어 있으며, 수치는 여기 옮겨 적지 않고 CSV를 직접 본다.

1회 추첨의 기댓값은 `Σ(value × weight) / Σ(weight)` ≈ **18.35** 다 (`coins.csv` 현재 값 기준 — 값이
바뀌면 이 숫자도 다시 계산해야 한다). `targets.csv`의
`coin_count`·`min_denom_id`는 현재 모든 대상에 `1`/`c1`을 넣은 자리표시자이며, 이 기댓값은 위 2절
이전의 대상별 원시 보상 기준선(예: 일반형 4)보다 훨씬 크다 — 아직 맞지 않는다.

**확정하지 않은 이유**: `coins.csv`는 공용 계약이라 saltlake00과의 합의 없이 가중치·액면 구조를
바꾸지 않기로 했다. 이슈 #176이 파괴 모델 재계산을 진행 중이므로, `coin_count`·`min_denom_id`·
가중치 테이블의 최종값은 #176 결과가 나온 뒤 한 번에 맞춘다. 그 전까지 위 표와 `targets.csv` 값은
**잠정**으로 읽는다 — 밸런스 산식이 아니라 개수·금액을 분리하는 배선이 맞는지만 검증했다.

### 코인 액면 확정 (2026-09-22, #217) — 위 잠정값을 대체한다

`.github/scripts/simulate_balance.py`에 `coins.csv` 추첨을 그대로 반영한 `draw_coin_lottery`를
추가해 재계산했다(#188 작업 중 발견한 문제 — 임시값 `coin_count=1`/`min_denom_id=c1`을 4종 모두
그대로 쓰면 파괴 보상이 사실상 `coins.csv` 5개 액면 중 하나를 그대로 뽑는 것과 같아, 평균은 올라도
**중앙값·하위 10%(p10)가 오히려 떨어지는** 문제가 있었다).

`value` 정책의 목표 선택 기준도 함께 고쳤다. `coin_mult`·`break_bonus`는 `Target.OnHit`이 더는
읽지 않는 죽은 열인데(코드 확인 완료, `CoinLottery.SumValue`만 지급액을 정한다) 시뮬레이터의 `value`
정책은 여전히 이 죽은 열로 목표를 골랐다. 이제는 실제 지급을 결정하는 `coin_count`·`min_denom_id`로
계산한 "내구도(hp)당 기대 지급액"이 가장 큰 목표를 고른다.

**타겟별 확정값**:

| 타겟 | coin_count | min_denom_id | 근거 |
|---|---|---|---|
| `normal`(일반형) | 1 | `c5` | 스폰의 60%를 차지해 하위 10%(p10)를 좌우한다. `c1`을 허용하면 최악의 경우 1코인짜리 파괴만 반복돼 p10이 무너진다 |
| `anchor`(거치형) | 1 | `c25` | hp 12로 가장 오래 투자해야 하는 목표. 낮은 액면대를 허용하면 고내구도 투자가 저평가된다 |
| `runner`(고속형) | 1 | `c1` | hp 1의 "미끼". 총 기대 지급액을 낮게 유지해 빠르고 잡기 쉬워 보여도 실제 보상은 크지 않은 원작 의도를 지킨다 |
| `tourist`(회복형) | 1 | `c5` | 주 가치는 스태미나 회복이지만 `c1` 하나만 나오면 무가치해 보이므로 최소 액면만 소폭 올린다 |

**재계산 결과** (시드 46 · 2,000회 · 1단계, `bill_amount=35` 기준 — 아래 "고지서 재조정" 참고):

| 정책 | 평균 | 중앙값 | p10 | p90 | 고지서 달성률 |
|---|---:|---:|---:|---:|---:|
| random | 91.33 | 25.0 | 5.0 | 125.0 | 39.0% |
| value | 152.92 | 45.0 | 15.0 | 215.0 | 71.3% |

임시값 상태(모든 타겟 `1`/`c1`)의 p10은 random 1.0·value 0.0이었다 — 나쁜 런에서는 거의 아무것도
못 벌었다는 뜻이다. 위 확정값은 p10을 5·15로 끌어올려 "운이 나빠도 고지서의 일부는 번다"를
만족한다. 달성률(39.0%/71.3%)도 코인 액면 도입 전 기준(37.0%/71.0%, 2절 위 표)과 거의 같아,
`bill_amount` 재조정과 함께 원래 겨냥했던 난이도 밴드를 그대로 유지한다.

**고지서 재조정이 필요했던 이유**: `coins.csv` 1회 추첨 기댓값(≈18.35)이 코인 액면 도입 전
대상별 원시 보상 기준선(정상형 4 안팎)보다 훨씬 커서, `coin_count`·`min_denom_id`를 어떻게 잡아도
전체 경제 규모가 도입 전보다 커진다 — `coins.csv` 가중치·액면 자체는 공용 계약이라 이 이슈에서
바꾸지 않았으므로 피할 수 없는 결과다. `stages.csv`의 `bill_amount`를 1단계 10→35로 올리고,
2·3단계는 기존 성장률(2.5배·2.6배)을 그대로 적용해 90·235로 조정했다 — 2·3단계는 아직 직접
재시뮬레이션하지 않은 값이라 작업 7.2(3단계 밸런싱 실측)에서 검증한다.

**`coin_mult`·`break_bonus` 두 열의 처리**: 코드 확인 결과 `BalanceImporter`의 값 검증(0 이상인지)
에만 쓰이고 실제 파괴 보상 지급(`Target.OnHit` → `CoinLottery.Draw`)에는 전혀 관여하지 않는 죽은
열이다. **제거가 맞다고 판단했다** — 같은 설계 의도(내구도가 높을수록 더 큰 보상)를 이제
`coin_count`·`min_denom_id`가 대신하고 있어 이 두 열은 완전히 중복이다. 다만 `targets.csv` 컬럼
제거는 CSV 스키마 변경이라 AGENTS.md 규칙상 구현 전에 별도 "공용 계약 변경" 이슈가 선행돼야 한다.
이번 이슈에서는 스키마를 건드리지 않고 **결정과 근거만 남기며**, 실제 제거는 후속 이슈
[#241](https://github.com/KDNA-Gwangju-1/NCAIClicker/issues/241)로 넘긴다.

## 4. 고지서·대출 — 구조 검사와 플레이 검증을 분리한다

`단계 목표 × 마감일수`는 수입 상한도 예상 수입도 아니다. 이전 임포터의 이 조건은 제거했다.
임포터는 납부 금액/기한의 유효 범위, 중복 ID, 출현 비율, 유한한 수치, 필수 열을 검사한다.
고지서를 실제로 낼 수 있는지와 대출 후 갚을 수 있는지는 작업 7.2에서 측정한다.

- 고지서 금액은 아래 "기준값 확정" 규칙으로 정한다. 핵심 판단이 생기는 부담 수준은
  실제 마감일까지 번 **순수입**과 업그레이드 지출 여력을 함께 보며 7.2에서 조정한다.
- 지표: 첫 마감 납부율, 마감 직전 가용 코인, 대출 후 완제까지 걸린 날짜, 파산 후 재성장 속도.
- 미납은 마감 선택 완료 후 파산이다. 데모의 추심 누적 삭감은 도입하지 않는다.
- 대출 수입 징수는 부채를 줄이지 않는다. 원금 입금은 런 수입에 포함하지 않는다.

### 고지서·대출 기준값 확정 (2026-09-16, #6)

`stages.csv`의 고지서 금액과 `bills.csv`의 마감 기본값·대출 계수를 7.2 실측 전 출발점으로 확정했다.
검산은 "하루 수입 = 그 단계 목표(런 1회 획득량 기준)"로 놓고, 업그레이드 비용은 `upgrades.csv`
공식으로 손으로 따라간 것이다. 업그레이드에 따른 수입 성장·회복형 연장은 반영하지 않았으므로
결론은 보수적이며, 실제 값은 7.2에서 측정한다.

- **고지서 한 장 = 그 단계의 관문이다.** 납부하면 단계가 오른다. 마감일은 단계가
  오를수록 짧아지므로 마감일 수입 대비 고지서 비중은 `1 / due_days`로 단계마다 커진다 — GDD의
  "날이 갈수록 압박이 누적된다"를 값 하나로 만든다.
- **파산에 도달할 수 있다.** 매일 남는 코인을 싼 업그레이드부터 전부 사는 플레이어는 세 단계 모두
  마감일 잔액이 고지서에 못 미친다. 이전 초기값(목표의 수 % 수준)은 1·2단계에서 파산이 불가능했다.
- **저축하면 조기 납부가 된다.** 좋은 런 한두 번 수입을 남기면 마감 첫날이나 둘째 날 낼 수 있어
  "지금 낼까, 업그레이드에 쓸까"가 매일의 선택으로 남는다.
- **대출은 갚을 수 있고 나선형 파산은 나지 않는다.** 고지서 전액을 빌리면 이자 포함 부채를 하루 수입
  이틀분 안에서 갚고, 징수 손실은 하루 수입의 일부 수준이라 "빌릴까 말까"의 비용이 된다.
  `bills.csv`의 이자·징수 범위·쿨다운·동시 건수는 변경 없이 확정한다.
- **`bills.csv`의 `due_days`는 기본값이다.** 실제 마감은 `stages.csv`를 우선하며(7절), 기본값은
  1단계 마감과 같게 유지한다.
- 파산 관련 새 열은 추가하지 않는다(GDD 파산 절). 미납 시 즉시 파산이며 정산 비율 항목이 없는 것이 정상이다.

## 5. 피버

게이지는 **적중**으로만 채운다. 호버·자동 망치의 적중 여부와 `HitSource`를 함께 전달하고,
정확도는 호버만 집계한다. 회복·스폰 대기로 적중 수가 달라지므로 런당 발동 횟수를 상수로 단정하지 않는다.
게이지·지속 시간·배율은 `fever.csv`를 따른다. 퍼크 선택 중에는 피버 시간도 멈춘다.

### 발동 빈도 검증 (2026-09-17, #31)

작업 5.1의 완료 기준이 "런당 2~3회 발동"이라 `simulate_balance.py` 에 발동 횟수 집계를 넣고
조준 성공률을 바꿔가며 쟀다. 각 3,000회, `random`·`value` 정책 및 시드 3개로 교차 확인했다.

**이전 `gauge_per_hit` 로는 기준을 만족하지 못했다.** 조준 성공률 0.6 이하에서는 한 번도
발동하지 않았고, 성공률 1.0 에서도 런당 1회에 그쳤다. 기본 런에 들어가는 스윙 수보다
발동에 필요한 적중 수가 많았던 것이다. 그래서 `gauge_per_hit` 를 올렸다.

| 조준 성공률 | 0.3 | 0.5 | 0.6 | 0.8 | 1.0 |
|---|---:|---:|---:|---:|---:|
| 평균 발동(회) | 0.12 | 1.28 | 1.96 | 2.77 | 3.02 |
| 런별 범위 | 0~1 | 0~2 | 1~2 | 2~3 | 3~4 |

**0.6~1.0 구간에서 평균 2~3회**로 기준을 만족한다. 성공률 0.3 의 서툰 플레이는 거의 발동하지
않는데, 피버가 숙련을 보상하는 장치이므로 의도한 모양이다.

`gauge_decay_per_sec` 는 건드리지 않았다. 절반으로 낮춰 봐도 발동 횟수가 거의 같았다 —
유예 시간 안에 다음 적중이 들어오는 경우가 대부분이라 감쇠가 총량을 좌우하지 않는다.

이 값은 **업그레이드·퍼크가 없는 첫 단계 기준**이다. "헬스장 회원권"(피버 지속·배율 강화)이
붙는 작업 3.3 이후에는 다시 뽑아야 한다.

## 6. 업그레이드 효과 — 어떤 수치를 건드리는지 표에서 지정한다

업그레이드는 두 파일로 나뉜다.

- `upgrades.csv` — 이름, 설명, 초기 비용, 최대 레벨, 표시 순서
- `upgrade_effects.csv` — **그 업그레이드가 어떤 수치를 얼마나 바꾸는지**

나눈 이유는, 업그레이드 하나가 여러 수치를 동시에 건드리기 때문이다. 예를 들어 강한 망치는 타격 파워와 판정 반경을 같이 올린다. 한 파일에 우겨넣으면 `effect1_stat`, `effect2_stat` 같은 열이 계속 늘어난다.

```csv
upgrade_id,stat,effect_type,value_per_level,note
strong_hammer,base_hit_power,add,0.35,레벨당 타격 피해량 +0.35
strong_hammer,hit_radius,percent,2,레벨당 피격 판정 반경 +2%
```

- `stat` — **무엇을 바꿀지.** 아래 표의 이름만 쓸 수 있다
- `effect_type` — `add`(그대로 더함) 또는 `percent`(기준값의 %만큼 더함)
- `value_per_level` — 레벨 1당 변화량

| `move_drain_per_unit` | `stamina.csv` → `move_drain_per_unit` | 원작형 규칙에서는 0으로 고정한 미사용 호환 필드 |
| `hit_drain_per_swing` | `stamina.csv` → `hit_drain_per_swing` | 원작형 규칙에서는 0으로 고정한 미사용 호환 필드 |

목록을 늘리려면 `BalanceData.cs` 의 `StatId` enum 에 항목을 추가하고, 이 표에 한 줄 적고, 화면에 띄울 한글 이름을 `Assets/Scripts/Runtime/UI/UpgradeStatNames.cs` 에 한 줄 더한다 (#91). 마지막을 빠뜨리면 상점 카드에 enum 이름이 그대로 노출된다 — 조용히 비지 않게 해 둔 것이다. **enum 에 없는 이름은 CSV에 적어도 임포트가 거부한다** — 오타가 런타임까지 가지 않게 하려는 의도다.

> 효과값은 `base × (1 + percent 합 / 100) + add 합`으로 계산하며 해당 레벨까지 누적한다.
> 비용은 `ceil(InitCost × CostGrowth^현재레벨)`이고 CostGrowth가 0이면 EconomyConfig 값을 쓴다.
> 구매는 메뉴/결과에서만 허용하고 다음 런에 반영한다. 직렬화된 BalanceData 원본을 변경하지 않는다.
> 단계 목표는 StageDef.GoalCoin이 우선이며 StageGoalGrowth는 새 단계값 산출 근거로만 쓴다.
> HitRadius 효과의 기준은 콜라이더 원래 반경이 아니라 CSV의 기본 확대 비율이다.

**"타격 범위"를 정하는 값은 두 축이고 서로 곱해지지 않는다.** 하나만 보고 판단하면 실측이 어긋난다.

| 축 | 값 | 무엇을 키우나 | 업그레이드 |
|---|---|---|---|
| 조준 반경 | `economy.csv` → `reticle_radius` | 커서 주변에서 대상을 찾는 거리 | **받지 않는다** |
| 대상 콜라이더 | `economy.csv` → `hit_radius_bonus` + 대상 프리팹의 기준 반경 | 맞는 쪽의 몸집 | `hit_radius` |

조준 반경을 업그레이드 대상으로 삼지 않는 이유는, 같은 "판정이 넓어진다"를 두 축에 걸면
효과가 두 번 곱해져 7.2 실측에서 어느 쪽이 기여했는지 분리되지 않기 때문이다 (#132).
반경 자체를 키우고 싶어지면 이 표를 먼저 고치고 구현한다.

### 이름만 바꾸고 싶을 때

`upgrades.csv` 의 `display_name` 과 `description` 만 고치면 된다. 수치와 무관하므로 밸런스에 영향이 없다. 게임 톤을 바꾸고 싶으면 여기만 손대면 된다.

### 코인 지급 모델 (변경됨)

**코인은 타격마다가 아니라 대상이 파괴될 때 한 번에 지급한다.**

```
파괴 시 지급 = (hp × coin_mult + break_bonus) × 피버 배율 × 보너스 배율
```

`coin_mult` 는 이제 **타격당 배율이 아니라 내구도 1당 배율**이다. 총량은 타격마다 주던 때와 같지만,
**끝까지 못 부순 대상은 0원**이라는 점이 다르다. 내구도가 곧 투자 시간이 된다.

### `due_days` 가 두 파일에 있는 이유

`bills.csv` 와 `stages.csv` 양쪽에 `due_days` 가 있다. **단계값이 우선이고 `bills.csv` 는 기본값이다**
(StageDef.DueDays가 0일 때만 BillConfig.DueDays를 쓴다). 음수는 임포트 오류다.

**모든 수치는 작업 7.2(밸런싱)에서 실측으로 검증한다.** 위 모델은 독립적인 조준 확률을 가정한다. 실제 플레이 로그와 다르면 모델의 가정을 먼저 고친다.
