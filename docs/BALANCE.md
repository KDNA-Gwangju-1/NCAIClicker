# 밸런스 설계표

모든 수치는 `Assets/GameData/Balance/*.csv`가 원본이다. 이 문서는 **왜 그 숫자가 됐는지**를 적는다. 숫자를 바꿀 때는 CSV를 고치고, 근거가 달라졌으면 이 문서도 같이 고친다.

## 1. CSV를 원본으로 삼는 이유

Unity에서 밸런스 데이터를 다루는 방법은 보통 ScriptableObject(이하 SO)다. 그런데 SO 에셋(`.asset`)은 YAML이라 **여러 명이 같은 파일을 고치면 Git 충돌이 나고, 충돌 해결이 어렵다.** [EXECUTION_PLAN.md](EXECUTION_PLAN.md)에서 이미 "공유 SO 동시 수정"을 위험으로 지목하고 LFS lock이나 채널 공지로 때우자고 적어둔 문제다.

CSV를 원본으로 두면 이 문제가 사라진다.

| | CSV 원본 | SO 직접 편집 |
|---|---|---|
| Git 충돌 | 행 단위 자동 병합 — 다른 행을 고치면 충돌 없음 | 파일 전체 충돌, 수동 해결 |
| 편집 도구 | Excel, Google Sheets, 메모장 | Unity 에디터를 켜야 함 |
| 리뷰 | PR diff에 `40 → 25`로 보임 | YAML 덩어리라 판독 어려움 |
| 타입 안전성 | 없음 (임포트 시 검증 필요) | 있음 |

**구조**: CSV는 원본, SO는 빌드 산출물이다.

```
Assets/GameData/Balance/*.csv   ← 사람이 고치는 원본 (PM이 Unity 없이도 수정 가능)
        ↓ 에디터 임포터 (Unity 에디터에서만 실행)
Assets/GameData/Generated/*.asset  ← 자동 생성 SO
        ↓ 런타임은 이것만 읽는다
```

런타임에서 CSV를 파싱하지 않는 것이 핵심이다. 빌드에 파서를 넣으면 문자열 파싱 실패가 그대로 런타임 크래시가 된다. 임포트는 에디터에서 끝내고, 실패하면 그 자리에서 콘솔 에러로 잡는다.

**규칙**: 생성된 SO는 손으로 고치지 않는다. 고쳐도 다음 임포트에 덮어써진다.

### 생성된 SO도 저장소에 커밋한다

산출물인데 왜 커밋하느냐 하면, **프리팹과 씬이 이 에셋을 GUID로 참조하기 때문**이다. 각자 로컬에서 생성하게 두면 사람마다 GUID가 달라져서, 내 PC에서 연결한 참조가 남의 PC에서 끊긴다.

임포터는 기존 에셋이 있으면 그것을 갱신하고 새로 만들지 않으므로 GUID는 한번 정해진 뒤 바뀌지 않는다 (현재 `148d52a3...`).

**병합 충돌이 나면 해결하지 말고 재임포트한다.** 생성물이므로 CSV만 맞으면 결과는 같다.

## 2. 스태미나 — 남은 시간을 보여주는 게이지

목표는 **한 런 60~90초**다. 발표 시연에서 한 판을 보여주고 결과까지 가야 하므로 그 이상은 길다.

원작처럼 스태미나가 계속 줄어들도록 하여 별도의 시간제한 UI를 대신한다. 커서 이동과 호버 타격에는 추가 비용을 붙이지 않는다. 따라서 플레이 방식과 관계없이 기본 런 길이는 일정하다.

1. 프로젝트의 임시 최대 스태미나를 **120**으로 둔다. 팀 플레이 기록에서 `34/120` HUD를 관찰했지만, 원작의 최초 기본 최대치인지는 확인되지 않았다. 따라서 120은 원작 복제값이 아니라 계산과 HUD 가독성을 위한 우리 기준값이다.
2. 목표 런 길이를 **75초**로 둔다.
3. 초당 감소량은 `120 / 75 = 1.6`으로 정한다.

가정: 커서가 대상 위에 있는 시간 비율 60%, 자동 스윙 0.15초 간격.

```
초당 소모 = 1.6
런 길이  = 120 / 1.6 = 75초
총 스윙  = 75 × 0.6 / 0.15 = 300회
```

런 길이를 고정에 가깝게 유지하면 플레이어는 스태미나를 아끼기 위해 멈추지 않고, 남은 시간 동안 자동 타격 효율을 높이는 데 집중한다. 스태미나 회복 퍼크는 남은 시간을 직접 늘리는 강한 효과이므로 소량만 제공한다.

## 3. 경제 — 1단계를 첫 런에 아슬아슬하게

300회 스윙, 1단계 대상 구성(일반 70% / 거치 20% / 고속 10%, 평균 코인 배율 1.08) 기준:

```
타격 코인    300 × 1.0 × 1.08 = 324
파괴 보너스  일반 70회×1 + 거치 5회×10 + 고속 30회×0 = 120
피버 추가    런당 2.4회 발동, 추가분 = 104
------------------------------------------------
1런 총 획득  548        (1단계 목표 500)
```

업그레이드를 하나도 안 산 첫 런에서 **548 대 500**으로 겨우 넘긴다. 의도한 난이도다. 표적을 놓치는 시간이 길면 미달하고, 그러면 코인은 남으니 업그레이드를 사서 재도전하게 된다.

**청구서는 런 안이 아니라 며칠에 걸쳐 온다.** 1단계는 마감 5일에 금액 25이므로, 5일 동안 약 2,740 을 버는 사이에 25 를 내면 된다 — 첫 단계는 거의 부담이 없고, 규칙을 익히는 구간이다.

부담은 단계가 오르며 마감이 짧아질 때 생긴다.

| 단계 | 마감 | 금액 | 마감일까지 예상 수입 | 비중 |
|---|---|---|---|---|
| 1 | 5일 | 25 | 약 2,740 | 1% |
| 2 | 4일 | 70 | 약 5,000 | 1.4% |
| 3 | 3일 | 190 | 약 9,400 | 2% |

지금 수치는 **의도적으로 낮게 잡았다.** 대출과 파산이 붙은 상태에서 청구서까지 무거우면 첫 플레이가 좌절스럽다. Day 4 밸런싱에서 실측한 뒤, 마감일 수입의 **25~35%** 가 되도록 금액을 끌어올린다. 그 구간을 넘으면 납부하는 순간 업그레이드를 살 돈이 없어 성장이 멈추고, 훨씬 아래면 그냥 다 내면 되니 판단이 사라진다.

단계 목표가 2.5배씩 오르므로(500 → 1,250 → 3,125), 청구서 금액도 같은 비율로 올린다(25 → 70 → 190).

## 4. 마감일 안에 낼 수 있는지 확인

청구서는 **마감일까지 못 내면 파산**이므로, 금액이 그 기간에 벌 수 있는 양을 넘으면 게임이 성립하지 않는다.

임포터가 이 조건을 자동으로 검사한다.

- `청구 금액 > 단계 목표 × 마감일수` → **임포트 실패.** 아무리 잘해도 못 내는 금액이다
- `청구 금액 > 그 절반` → **경고.** 낼 수는 있지만 업그레이드 여력이 없어 성장이 멈춘다

> 마감일을 줄이거나 금액을 올리는 밸런싱을 하면 이 계산이 바뀐다. 문서에 적어두면 잊히므로 코드로 옮겼다 — 임포트할 때마다 자동으로 확인된다.

### 대출이 구제책으로 작동하는지

대출은 마감일에 돈이 모자랄 때만 의미가 있다. 이자 10% 에 매일 수입의 5~10% 를 징수당하므로, **하루 수입의 절반을 넘는 금액을 빌리면 상환 자체가 어려워진다.** Day 4 밸런싱에서 "빌려서 살아남은 뒤 실제로 갚아지는가"를 실측한다.

## 5. 피버

게이지 100, 타격당 0.8 누적 → **125회 타격에 1회 발동**, 런당 2~3회. 런당 1회면 있으나 마나고, 5회를 넘으면 상시 피버가 되어 배율의 의미가 사라진다.

## 6. 업그레이드 효과 — 어떤 수치를 건드리는지 표에서 지정한다

업그레이드는 두 파일로 나뉜다.

- `upgrades.csv` — 이름, 설명, 초기 비용, 최대 레벨, 표시 순서
- `upgrade_effects.csv` — **그 업그레이드가 어떤 수치를 얼마나 바꾸는지**

나눈 이유는, 업그레이드 하나가 여러 수치를 동시에 건드리기 때문이다. 예를 들어 강한 망치는 타격 파워와 판정 반경을 같이 올린다. 한 파일에 우겨넣으면 `effect1_stat`, `effect2_stat` 같은 열이 계속 늘어난다.

```csv
upgrade_id,stat,effect_type,value_per_level,note
strong_hammer,base_hit_power,add,0.35,레벨당 타격 코인 +0.35
strong_hammer,hit_radius,percent,2,레벨당 피격 판정 반경 +2%
```

- `stat` — **무엇을 바꿀지.** 아래 표의 이름만 쓸 수 있다
- `effect_type` — `add`(그대로 더함) 또는 `percent`(기준값의 %만큼 더함)
- `value_per_level` — 레벨 1당 변화량

### stat 이름이 가리키는 기준값

`stat` 에 적는 이름은 임의 문자열이 아니라 **정해진 목록**이며, 각각 어느 CSV의 어느 값을 기준으로 삼는지가 아래처럼 고정되어 있다. 오타를 적으면 임포트가 실패하면서 쓸 수 있는 이름 목록을 콘솔에 출력한다.

| stat 이름 | 기준값이 있는 곳 | 의미 |
|---|---|---|
| `base_hit_power` | `economy.csv` → `base_hit_power` | 타격 1회 기본 코인 |
| `hit_radius` | `economy.csv` → `hit_radius_bonus` | 피격 판정 확대 비율 |
| `auto_hammer_count` | `economy.csv` → `auto_hammer_count_init` | 자동 망치 보유 수 |
| `auto_hammer_power` | `economy.csv` → `auto_hammer_power` | 자동 망치 타격당 코인 |
| `auto_hammer_hits_per_sec` | `economy.csv` → `auto_hammer_hits_per_sec` | 자동 망치 초당 타격 |
| `coin_bonus_multiplier` | `economy.csv` → `coin_bonus_multiplier` | 보너스 배율 |
| `spawn_count` | `stages.csv` → `spawn_count` | 동시 출현 저금통 수 |
| `spawn_interval_sec` | `economy.csv` → `spawn_interval_sec` | 재등장 대기 시간 |
| `fever_duration` | `fever.csv` → `duration_sec` | 피버 지속 시간 |
| `fever_multiplier` | `fever.csv` → `coin_multiplier` | 피버 코인 배율 |
| `fever_gauge_per_hit` | `fever.csv` → `gauge_per_hit` | 피버 게이지 누적량 |
| `max_stamina` | `stamina.csv` → `max_stamina` | 최대 스태미나 |
| `idle_drain_per_sec` | `stamina.csv` → `idle_drain_per_sec` | 초당 기본 소모 |
| `move_drain_per_unit` | `stamina.csv` → `move_drain_per_unit` | 원작형 규칙에서는 0으로 고정한 미사용 호환 필드 |
| `hit_drain_per_swing` | `stamina.csv` → `hit_drain_per_swing` | 원작형 규칙에서는 0으로 고정한 미사용 호환 필드 |

목록을 늘리려면 `BalanceData.cs` 의 `StatId` enum 에 항목을 추가하고 이 표에 한 줄 적는다. **enum 에 없는 이름은 CSV에 적어도 임포트가 거부한다** — 오타가 런타임까지 가지 않게 하려는 의도다.

> **이 값들을 실제로 어떻게 적용할지는 3번(성장·저장) 담당이 정한다.** CSV와 `BalanceData` 는 "무엇을 얼마나 바꾼다"는 선언만 담고, 계산 순서나 적용 시점은 구현자의 영역이다.

### 이름만 바꾸고 싶을 때

`upgrades.csv` 의 `display_name` 과 `description` 만 고치면 된다. 수치와 무관하므로 밸런스에 영향이 없다. 게임 톤을 바꾸고 싶으면 여기만 손대면 된다.
