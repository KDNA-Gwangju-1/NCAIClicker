## Unity 구조와 협업 계약

- 메인 씬은 통합 담당자만 단독 수정한다.
- 팀원은 프리팹과 독립 스크립트 단위로 작업한다.
- 공용 인터페이스와 이벤트는 Day 1 이후 임의로 변경하지 않는다. 구체적인 인터페이스·매니저·이벤트 목록은 [ARCHITECTURE.md](ARCHITECTURE.md)를 따른다.
- Game, Economy, UI 이벤트를 철저히 분리하여 스크립트 간 직접 참조를 차단한다.
- 설정값은 ScriptableObject, 저장값은 별도 SaveData DTO로 관리한다.
- Unity 버전과 패키지를 고정하고 meta 파일을 함께 커밋한다.
- 한 작업은 한 브랜치와 한 PR 단위로 처리한다.
- PR 본문에 작업 이슈, 변경 범위, 검증 결과를 기록한다.

### PR 리뷰·머지 규칙

- 브랜치명 규칙: `feature/<모듈>-<이슈번호>-설명` (예: `feature/economy-12-upgrade-cost`)
- PR은 담당자 본인이 아닌 리뷰어 최소 1명의 승인을 받아야 머지한다 — 본인 모듈을 스스로만 리뷰하면 교차 검증 효과가 없으므로, 1번(PM·기획·통합) 담당이 리뷰어를 순환 배정한다.
- 머지 전략은 Squash and merge로 통일한다.

### 충돌 관리

- 메인 씬·프리팹 단독 작업 원칙만으로는 여러 담당자가 함께 참조하는 공유 ScriptableObject(경제 밸런스 데이터 등)의 동시 수정까지는 막지 못한다.
- `.gitattributes`에 UnityYAMLMerge(스마트 병합)를 설정해 씬·프리팹의 텍스트 기반 병합 성공률을 높인다.
- 여러 담당자가 참조하는 공유 SO 파일은 Git LFS lock으로 편집 중임을 표시하거나, LFS 설정이 부담되면 팀 채널에 "economy.asset 수정 중" 한 줄 공지로 대체한다.
- 브랜치 수명은 하루 이내로 짧게 유지하고 매일 main을 rebase 또는 pull해 충돌을 작을 때 조기에 발견한다.
- 업무 배분 자체의 중복(두 명이 같은 이슈를 동시에 집는 것)은 GitHub Projects 보드에서 이슈 담당자 지정과 "In Progress" 전환을 명확히 해 방지한다.
- 매일 5~10분 데일리 싱크(어제 한 일 / 오늘 할 일 / 블로커)로 겹치는 작업과 충돌 소지를 조기에 걸러낸다.

## 에이전트(AI 코딩 어시스턴트) 작업 규칙

- 작업 착수 직전 GitHub Issue의 담당자·상태 필드를 재확인한다. 비어 있거나 본인 배정 상태일 때만 착수하고, 확인 즉시 담당자를 자신으로 지정한 뒤 상태를 In Progress로 바꾼다 — 확인과 상태 변경 사이 간격을 최소화해 두 에이전트가 같은 이슈에 동시 착수하는 것을 막는다.
- 한 에이전트는 한 모듈의 작업만 전담한다.
- 기존 공용 계약을 변경해야 할 경우 구현 전에 별도 이슈를 발의한다.
- 코드 작성 후 반드시 Edit Mode 또는 Play Mode 검증 결과를 기록한다.
- 진행률을 임의로 추측하지 않고 Ready, In Progress, In Review, Done, Blocked 상태를 엄격히 사용한다.
- PR이 생성되면 In Review, 병합되면 Done으로 상태를 갱신한다.
- 에이전트는 메인 씬과 타 담당자의 프리팹을 직접 수정하지 않는다.
- 작업 브랜치에서 일정 간격(커밋 3회 또는 30분마다)과 PR 생성 직전에는 반드시 `git fetch origin main && git rebase origin/main`으로 최신 main을 받아온다. 병합 커밋 대신 그 자리에서 리베이스 충돌을 해결하고 이어서 작업한다.
- 리베이스 중 공용 인터페이스·이벤트·ScriptableObject 필드가 바뀐 것을 발견하면 임의로 두 버전을 섞어 계속 진행하지 말고 작업을 멈춘 뒤 해당 이슈에 코멘트로 보고한다.

## 완료 조건

- 스태미나가 소진될 때까지 한 런을 시작부터 정산 결과까지 반복 플레이할 수 있다.
- 호버 자동 타격과 자동 망치가 동일한 경제 수식 규칙을 준수한다.
- 청구서가 주기적으로 발생하고, 방치 시 추심원 페널티가 실제로 수익에 반영된다.
- 업그레이드 효과가 다음 런에 즉각 반영된다.
- 단계 목표 달성 여부와 누적 금액이 명확히 시각화된다.
- 게임 재실행 시에도 SaveData DTO를 통해 핵심 성장 데이터가 유지된다.
- 16:9 해상도 기준으로 제작하되, PC의 다양한 모니터 해상도에서 HUD가 잘리거나 깨지지 않는다.
- 최종 플랫폼 빌드에서 치명적인 런타임 오류가 없다.

## 기술 결정 및 Day 1 확정 항목

### 사전 확정 완료 사항

- 렌더링 방식: 2D 스프라이트 기반 (Canvas UI 및 2D 렌더러)
- 화면 비율: 16:9 가로 고정 비율
- 조작: 클릭 연타 대신 호버 자동 스윙 (0.15초 간격 자동 타격)
- 타격 판정: 피격 콜라이더 25% 확장
- 판 길이: 고정 시간 대신 스태미나 게이지 소진까지
- 자동 망치: 물리 충돌 대신 글로벌 타이머 기반 무조건 자동 적중
- 단계별 목표: 1단계 500, 2단계 1,250, 3단계 3,125 코인

### Day 1 킥오프 미팅 확정 항목

- 단계별 타격 대상 외형 리소스 선정
- 외부 트윈 라이브러리(LeanTween vs DOTween) 도입 여부
- SaveData DTO 필드 및 JSON 직렬화 규격
- 추가 목표(미니게임 등) 착수 우선순위
- 경제 공식 기준값(기본 타격 파워, 망치 파워, 초기 자동 망치 수, 업그레이드 초기 비용) 확정
- 스태미나 소모·회복 계수(이동/타격당 소모량, 피버 중 소모 감소율) 확정
- 청구서 발생 주기·금액, 추심원 페널티 비율, 납부 퍼크 종류 확정
