# 실행 계획

[GDD.md](GDD.md)의 MVP를 5명이 모듈별로 나눠 만든다. 작업은 날짜가 아니라 **선후 관계**로 정리했다 — 선행이 끝나면 착수하고, 병행 가능한 것은 동시에 진행한다.

각 작업은 GitHub 이슈와 1:1로 대응하며 [칸반 보드](https://github.com/orgs/KDNA-Gwangju-1/projects/2/views/2)에서 상태를 추적한다.

## 역할 분담

| 담당 | 책임 |
|---|---|
| 1. PM·기획·통합 | 규칙, 밸런스, 데이터, PR 관리, 통합 빌드, 발표 |
| 2. 코어 플레이 | 호버 자동 타격, 이동, 스태미나, 상태 머신, 목표 판정 |
| 3. 성장·저장 | 자동 망치, 업그레이드, 경제, 청구서·대출·파산, 저장, 최고 기록 |
| 4. 피버·보너스 | 피버 게이지, 배율, 청구서 납부 퍼크 |
| 5. UI·연출 | HUD, 결과 화면, 애니메이션, 파티클, 사운드 |

## 작업 구조

번호는 **날짜가 아니라 작업 순서**다. "Day 3에 하는 일"이 아니라 "3번 작업"이며, **선행 조건이 끝나면 바로 착수한다.** 하루가 남았다고 멈추지 않고, 하루가 밀렸다고 계획 전체가 밀리지도 않는다.

- **선행** 열이 비어 있으면 지금 당장 시작할 수 있다.
- 같은 선행을 가진 작업끼리는 **병행 가능**하다. 담당이 다르면 동시에 진행한다.
- **목표** 열은 참고용 기준선이다. 여기서 이틀 이상 벌어지면 범위 축소를 검토한다.

> **완료 기준은 여기 적지 않는다.** 각 작업은 같은 번호의 GitHub 이슈와 1:1로 대응하며, 담당·선행·완료 기준의 **정본은 이슈 본문**이다. 이 표는 전체 구조와 순서를 한눈에 보기 위한 지도일 뿐이다. 두 곳에 같은 내용을 적으면 한쪽이 반드시 낡는다.

## Unity 구조와 협업 계약

- 씬은 `MainMenu` / `Game` 2개이며 각각 소유자가 정해져 있다 ([ARCHITECTURE.md](ARCHITECTURE.md) 0절). **자기 씬이 아닌 씬은 열어서 보되 저장하지 않는다.**
- 소유자가 아닌 사람이 씬에 무언가를 넣어야 하면, 씬을 직접 고치지 말고 **프리팹으로 만들어 넘긴다.** 씬 파일은 병합이 가장 어려운 파일이다.
- 팀원은 프리팹과 독립 스크립트 단위로 작업한다.
- 공용 인터페이스와 이벤트는 Day 1 이후 임의로 변경하지 않는다. 구체적인 인터페이스·매니저·이벤트 목록은 [ARCHITECTURE.md](ARCHITECTURE.md)를 따른다.
- Game, Economy, UI 이벤트를 철저히 분리하여 스크립트 간 직접 참조를 차단한다.
- 정적 이벤트는 `OnEnable` 구독 / `OnDisable` 해제를 쌍으로 강제한다 ([ARCHITECTURE.md](ARCHITECTURE.md) 3절 구독 해제 규칙). 리뷰어는 PR에서 이 쌍이 맞는지 확인한다.
- 밸런스 수치의 원본은 `Assets/GameData/Balance/*.csv`다. ScriptableObject는 CSV에서 자동 생성되는 산출물이므로 손으로 고치지 않는다 ([BALANCE.md](BALANCE.md) 1절). 저장값은 별도 SaveData DTO로 관리한다.
- 모듈별로 따라야 할 설계 패턴은 [PATTERNS.md](PATTERNS.md)에 정리했다. 작업 착수 전 자기 담당 절을 읽는다.
- Unity 버전과 패키지를 고정하고 meta 파일을 함께 커밋한다.
- 한 작업은 한 브랜치와 한 PR 단위로 처리한다.
- PR 본문에 작업 이슈, 변경 범위, 검증 결과를 기록한다.

### PR 리뷰·머지 규칙

- 브랜치명 규칙: `feature/<모듈>-<이슈번호>-설명` (예: `feature/economy-12-upgrade-cost`)
- PR은 담당자 본인이 아닌 리뷰어 최소 1명의 승인을 받아야 머지한다 — 본인 모듈을 스스로만 리뷰하면 교차 검증 효과가 없으므로, 1번(PM·기획·통합) 담당이 리뷰어를 순환 배정한다.
- 머지 전략은 Squash and merge로 통일한다.

### 충돌 관리

- 메인 씬·프리팹 단독 작업 원칙만으로는 여러 담당자가 함께 참조하는 공유 ScriptableObject(경제 밸런스 데이터 등)의 동시 수정까지는 막지 못한다.
- `.gitattributes`에 UnityYAMLMerge(스마트 병합)를 설정해 씬·프리팹의 텍스트 기반 병합 성공률을 높인다.
- 밸런스 데이터는 CSV를 원본으로 삼아 이 충돌을 구조적으로 없앴다 — CSV는 Git이 행 단위로 병합하므로 서로 다른 행을 고치면 충돌하지 않는다. 자동 생성된 SO가 충돌하면 해결하지 말고 재임포트한다.
- 브랜치 수명은 하루 이내로 짧게 유지하고 매일 main을 rebase 또는 pull해 충돌을 작을 때 조기에 발견한다.
- 업무 배분 자체의 중복(두 명이 같은 이슈를 동시에 집는 것)은 GitHub Projects 보드에서 이슈 담당자 지정과 "In Progress" 전환을 명확히 해 방지한다.
- 매일 5~10분 데일리 싱크(어제 한 일 / 오늘 할 일 / 블로커)로 겹치는 작업과 충돌 소지를 조기에 걸러낸다.

## 에이전트(AI 코딩 어시스턴트) 작업 규칙

- 작업 착수 직전 GitHub Issue의 담당자·상태 필드를 재확인한다. 비어 있거나 본인 배정 상태일 때만 착수하고, 확인 즉시 담당자를 자신으로 지정한 뒤 상태를 In Progress로 바꾼다 — 확인과 상태 변경 사이 간격을 최소화해 두 에이전트가 같은 이슈에 동시 착수하는 것을 막는다.
- 한 에이전트는 한 모듈의 작업만 전담한다.
- 기존 공용 계약을 변경해야 할 경우 구현 전에 별도 이슈를 발의한다.
- 코드 작성 후 반드시 Edit Mode 또는 Play Mode 검증 결과를 기록한다.
- 진행률을 임의로 추측하지 않고 Ready, In Progress, In Review, Done, Blocked 상태를 엄격히 사용한다.
- PR이 생성되면 In Review, 병합되면 Done으로 상태를 갱신한다.
- 에이전트는 메인 씬과 타 담당자의 프리팹을 직접 수정하지 않는다.
- 작업 브랜치에서 일정 간격(커밋 3회 또는 30분마다)과 PR 생성 직전에는 반드시 `git fetch origin main && git rebase origin/main`으로 최신 main을 받아온다. 병합 커밋 대신 그 자리에서 리베이스 충돌을 해결하고 이어서 작업한다.
- 리베이스 중 공용 인터페이스·이벤트·ScriptableObject 필드가 바뀐 것을 발견하면 임의로 두 버전을 섞어 계속 진행하지 말고 작업을 멈춘 뒤 해당 이슈에 코멘트로 보고한다.

## 완료 조건

- 스태미나가 소진될 때까지 한 런을 시작부터 정산 결과까지 반복 플레이할 수 있다.
- 호버 자동 타격과 자동 망치가 동일한 경제 수식 규칙을 준수한다.
- 청구서가 마감일을 달고 도착하고, 조기 납부가 가능하다.
- 마감일까지 미납하면 파산으로 회차가 끝나고, 결과 화면이 "파산"으로 구분되어 표시된다.
- 대출을 쓰면 상환 전까지 매일 수입이 실제로 징수된다.
- 업그레이드 효과가 다음 런에 즉각 반영된다.
- 정확도가 런 단위로 집계되어 HUD와 결과 화면에 표시된다.
- 부서진 저금통이 일정 시간 뒤 다시 채워지고, 업그레이드로 그 수와 주기가 바뀐다.
- 단계 목표 달성 여부와 누적 금액이 명확히 시각화된다.
- 게임 재실행 시에도 SaveData DTO를 통해 핵심 성장 데이터가 유지된다.
- 16:9 해상도 기준으로 제작하되, PC의 다양한 모니터 해상도에서 HUD가 잘리거나 깨지지 않는다.
- 최종 플랫폼 빌드에서 치명적인 런타임 오류가 없다.

## 기술 결정 및 Day 1 확정 항목

### 사전 확정 완료 사항

- 렌더링 방식: **3D** — 3D 저폴리 오브젝트, 고정 탑다운 카메라, URP 기본 렌더러. 에셋은 VARCO 3D 로 생성한다
- 화면 비율: 16:9 가로 고정 비율
- 조작: 클릭 연타 없음. **망치는 0.15초 주기로 상시 스윙**하고 커서는 그 스윙이 닿을 대상을 고른다 (조준 유지형)
- 타격 판정: 피격 콜라이더 25% 확장
- 판 길이: 고정 시간 대신 스태미나 게이지 소진까지 (초당 기본 소모 상시 적용 — 원작 플레이로 확인, 방치로 무한 연장 불가)
- 자동 망치: 물리 충돌 대신 글로벌 타이머 기반 무조건 자동 적중
- 단계별 목표: 1단계 500, 2단계 1,250, 3단계 3,125 코인 (런 1회 내 획득량 기준)
- 한 번의 런 = 게임 속 하루. 청구서는 며칠 뒤 마감을 달고 오며 조기 납부 가능
- 마감일까지 미납하면 파산 — 회차 종료 후 영구 업그레이드만 유지하고 1일차 재시작
- 대출(빅 토니): 두 번째 청구서부터. 이자 10%, 매일 수입 5~10% 징수, 징수분은 부채를 줄이지 않음
- 코인 배율 적용 지점: 피버 배율·대출 징수는 EconomyManager 단독 적용, 호출측은 원시값만 전달

### Day 1 킥오프 미팅 확정 항목

- 카메라 확정 **(2. 코어 플레이 담당)**: 투영 방식(Perspective / Orthographic), 내려다보는 각도, 거리, 화각. 실제로 씬에 세워보고 담당자가 판단해 정한 뒤 팀에 공유한다. 한번 정하면 모든 에셋의 보이는 크기와 이동 안전 영역이 여기에 맞춰지므로 **Day 1 오전 중에** 끝낸다
  - 원작은 책상이 원근으로 물러나 보이므로 Perspective 에 가깝다. 다만 Orthographic 은 깊이에 따른 크기 변화가 없어 **타격 대상의 겉보기 크기가 위치와 무관하게 일정**해진다 — 피격 판정의 체감이 균일해지는 이점이 있으므로 둘을 실제로 띄워보고 정한다
- VARCO 3D 내보내기 포맷과 스케일 기준 확정 ([ASSET_PIPELINE.md](ASSET_PIPELINE.md) 2절)
- 단계별 타격 대상 외형 리소스 선정
- 외부 트윈 라이브러리(LeanTween vs DOTween) 도입 여부
- SaveData DTO 필드 및 JSON 직렬화 규격 ([ARCHITECTURE.md](ARCHITECTURE.md) 2절 초안 확정)
- 추가 목표(미니게임 등) 착수 우선순위
- 경제 공식 기준값(기본 타격 파워, 망치 파워, 초기 자동 망치 수, 업그레이드 초기 비용) 확정
- 스태미나 소모·회복 계수(**초당 지속 감소량**, 퍼크 회복량) 확정 — 기본 감소량은 목표 런 길이(60~90초)에서 역산하며, 이동·타격 추가 소모와 피버 중 감소 완화는 쓰지 않는다
- 단계별 청구서 마감일(기본 5/4/3일)과 금액, 납부 퍼크 종류 확정
- 대출 계수 확정: 이자율, 일일 징수 비율, 재대출 쿨다운 — 마감일 안에 낼 수 있는 금액인지는 임포터가 자동 검사한다 ([BALANCE.md](BALANCE.md) 4절)
- 파산 기준치 확정: 미납 허용 건수(기본 3건)와 파산 시 정산 비율(기본 50%) — 목표 런 길이 안에 청구서가 3건 이상 도착하는지 먼저 계산해서, 파산이 실제로 도달 가능한 상태인지 확인한다
