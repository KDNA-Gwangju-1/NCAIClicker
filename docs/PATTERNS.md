# 이 프로젝트에서 쓰는 설계 패턴

각 패턴이 **어디에 쓰이고, 왜 그걸 골랐고, 누가 담당하는지**를 적는다. 개인 학습용 목차이자, 에이전트에게 작업을 맡길 때 "이 모듈은 이 패턴으로 짜라"고 지정하는 근거로 쓴다.

패턴을 많이 쓰는 게 목적이 아니다. 7일짜리 5인 프로젝트에서 패턴은 **여러 명이 서로를 기다리지 않고 동시에 작업하기 위한 도구**일 때만 값어치를 한다. 그래서 8절에 "안 쓰는 패턴과 그 이유"도 같이 적었다 — 쓰지 않기로 한 결정도 결정이다.

---

## 1. Data-Driven Design (DDD)

> 로직은 코드에, 수치는 데이터 파일에. 수치를 바꾸는 데 컴파일이 필요 없게 만든다.

- **어디**: `Assets/GameData/Balance/*.csv` → 에디터 임포터 → SO → 런타임
- **왜**: 밸런스는 통합·밸런싱 단계(7.x)에서 수십 번 바뀐다. 코드 상수로 박아두면 그때마다 프로그래머가 붙잡혀야 하고, 기획 담당이 스스로 못 고친다. CSV 원본은 Git에서 행 단위로 병합되므로 **여러 명이 서로 다른 행을 동시에 고쳐도 충돌하지 않는다** — SO를 직접 편집할 때 생기는 가장 큰 문제를 없앤다.
- **담당**: 전원 (각자 자기 모듈 CSV)
- **상세**: [BALANCE.md](BALANCE.md)
- **학습 포인트**: "이 값이 바뀔 가능성이 있나?"를 기준으로 코드와 데이터를 가르는 감각. 바뀌지 않을 값까지 데이터로 빼면 추적만 어려워진다.

## 2. Singleton (싱글톤)

> 게임 전체에 하나만 존재하는 객체에 어디서든 접근하게 한다.

- **어디**: `GameManager`, `EconomyManager` 등 매니저 9종
- **왜**: DI 컨테이너(Zenject, VContainer)는 배우고 세팅하는 데만 하루가 든다. 7일 일정에서 그 하루는 없다.
- **담당**: [ARCHITECTURE.md](ARCHITECTURE.md) 담당 매핑표 참고
- **학습 포인트**: 싱글톤은 **남용하면 전역 변수와 같아진다.** 이 프로젝트가 싱글톤을 써도 무너지지 않는 이유는 매니저끼리 서로를 직접 부르지 않고 3번(이벤트 버스)으로 통신하기 때문이다. 싱글톤 자체보다 "싱글톤을 쓰되 결합은 막는 장치"가 핵심이다. 초기화 순서 의존도 싱글톤의 대표적 함정이라 ARCHITECTURE에 순서를 못 박아뒀다.

## 3. Observer / Event Bus (관찰자, 이벤트 버스)

> 누가 듣는지 모르는 채로 "이런 일이 일어났다"고 방송한다.

- **어디**: `GameEvents` 정적 클래스 (`OnCoinEarned`, `OnBillIssued`, `OnBankrupt` 등)
- **왜**: 5명이 병렬로 작업하려면 **상대 코드가 아직 없어도 내 코드를 짤 수 있어야** 한다. UI 담당(5번)은 EconomyManager 구현을 몰라도 `OnCoinEarned`만 구독하면 된다. 스크립트 간 직접 참조 차단이라는 협업 규칙을 코드로 강제하는 장치다.
- **담당**: 계약은 1번이 관리, 발행/구독은 전원
- **학습 포인트**: **구독 해제를 빠뜨리면 반드시 버그가 난다.** 정적 이벤트는 씬을 다시 로드해도 구독이 남아서, 코인이 2배로 들어오거나 파괴된 오브젝트를 참조해 예외가 터진다. `OnEnable` 구독 / `OnDisable` 해제를 쌍으로 쓰는 습관이 이 패턴의 절반이다.

## 4. State Machine (상태 머신, FSM)

> 객체가 가질 수 있는 상태를 열거하고, 상태 사이의 전이만 허용한다.

- **어디**: 두 군데
  - `GameManager` 런 상태: `MainMenu → Running → Result`
  - 타격 대상 행동: `Idle → Moving → BeingHit → Fleeing`
- **왜**: 행동 트리(BT)는 "공격할까 도망갈까 순찰할까"처럼 여러 목표의 우선순위를 저울질할 때 이점이 있는데, 타격 대상은 "이동 → 피격 → 경직 → 재이동"이라는 선형 전이뿐이다. BT를 쓰면 노드 설계·디버깅 비용만 늘고 얻는 게 없다.
- **담당**: 2. 코어 플레이
- **학습 포인트**: `enum` + `switch`로 시작해서 부족할 때 클래스로 승격하는 순서. 처음부터 상태마다 클래스를 만들면 이 규모에선 파일만 늘어난다. 그리고 **로직 상태와 애니메이션 상태를 분리**해두면 아티스트가 애니메이션만 건드릴 때 코드 충돌이 안 난다.

## 5. Interface Segregation / DIP (인터페이스 분리, 의존 역전)

> 구현이 아니라 계약에 의존한다. 계약은 잘게 나눈다.

- **어디**: `IHittable`, `IEconomyService`, `IBillService`, `ISaveService`
- **왜**: 코어 플레이이 타격을 구현할 때 성장·저장의 EconomyManager가 완성됐는지 기다릴 필요가 없다. `IEconomyService`만 있으면 가짜 구현으로 먼저 돌려볼 수 있다. **인터페이스는 팀원 사이의 약속이지, 코드 장식이 아니다.**
- **담당**: 계약 확정은 1번, 구현은 각 담당
- **학습 포인트**: 인터페이스를 크게 하나 만드는 것보다 역할별로 쪼개는 쪽이 낫다는 것. `ISaveService`가 저장만 담당하니까 UI 담당은 저장 내부를 몰라도 결과 화면을 만들 수 있다.

## 6. DTO (Data Transfer Object)

> 로직 없이 데이터만 담아 경계를 넘긴다.

- **어디**: `SaveData` (JSON 직렬화), `HitInfo` (타격 정보 전달)
- **왜**: 저장 포맷이 게임 로직 클래스와 얽히면, 클래스를 리팩터링할 때마다 세이브 파일이 깨진다. DTO로 분리하면 저장 포맷만 따로 관리된다. `SaveData.Version` 필드를 둔 것도 같은 이유 — 필드가 바뀌어도 옛 세이브를 읽을 길을 남긴다.
- **담당**: 3. 성장·저장
- **학습 포인트**: DTO에는 메서드를 넣지 않는다. 넣는 순간 DTO가 아니라 그냥 클래스가 되고, 직렬화 경계가 흐려진다.

## 7. Object Pool (오브젝트 풀)

> 생성·파괴를 반복하는 대신 미리 만들어두고 껐다 켠다.

- **어디**: 코인 파티클, 숫자 팝업, 타격 이펙트
- **왜**: 런당 300회 타격이면 숫자 팝업이 300개 생성·파괴된다. 그대로 두면 GC 스파이크로 프레임이 튄다. ARCHITECTURE 의 작업 7.3 점검 항목에 "GC 스파이크(파티클·숫자 팝업 인스턴스화)"가 들어간 이유다.
- **담당**: 5. UI·연출
- **학습 포인트**: Unity 2021+에는 `UnityEngine.Pool.ObjectPool<T>`가 기본 제공된다. 직접 만들지 말 것. 그리고 **풀에서 꺼낼 때 상태 초기화를 빠뜨리는 것**이 이 패턴의 단골 버그다 (이전 값이 남은 숫자 팝업이 그대로 뜨는 식).

## 8. 쓰지 않기로 한 것

| 패턴/도구 | 안 쓰는 이유 |
|---|---|
| DI 컨테이너 (Zenject, VContainer) | 학습·세팅에 하루 이상. 싱글톤+이벤트 버스로 같은 목적 달성 가능 |
| 행동 트리 (BT) | 타격 대상 행동이 선형 전이뿐이라 FSM으로 충분 (4절 참고) |
| 메시징 프레임워크 (UniRx, MessagePipe) | C# 기본 `event`로 충분. 패키지 의존성을 늘리는 쪽이 더 위험 |
| Service Locator | 매니저가 9개뿐이고 싱글톤으로 이미 접근 가능. 한 겹 더 씌울 이유 없음 |
| Command 패턴 (실행 취소) | 되돌릴 동작이 없는 게임이라 쓸 데가 없음 |
| ECS / DOTS | 동시 객체가 10개 미만. 얻을 성능이 없고 학습 비용만 큼 |

새 패턴을 도입하고 싶으면 **"이게 없으면 지금 누가 막히는가"에 답할 수 있어야 한다.** 답이 안 나오면 도입하지 않는다.

## 9. 담당별 학습 경로

작업 시작 전에 자기 담당 패턴을 먼저 읽는다. 에이전트에게 작업을 맡길 때도 이 매핑을 근거로 "이 모듈은 N절 패턴을 따르라"고 지정한다.

| 담당 | 먼저 읽을 것 |
|---|---|
| PM·기획·통합 | 1(DDD), 3(이벤트 버스), 5(인터페이스) — 계약을 관리하는 자리 |
| 코어 플레이 | 4(FSM), 5(인터페이스), 2(싱글톤) |
| 성장·저장 | 6(DTO), 5(인터페이스), 1(DDD) |
| 피버·보너스 | 3(이벤트 버스), 1(DDD) |
| UI·연출 | 3(이벤트 버스), 7(오브젝트 풀) |
