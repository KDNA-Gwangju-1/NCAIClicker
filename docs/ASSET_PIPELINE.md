# 3D 에셋 파이프라인

그래픽은 **3D**로 확정했다. 에셋 제작은 **VARCO 3D**로 한다.

7일 일정에서 3D의 가장 큰 위험은 폴리곤 수도 렌더링 비용도 아니고, **에셋이 안 나와서 개발이 멈추는 것**이다. 이 문서의 절반은 그걸 막는 규칙이다.

## 1. 그레이박스 우선 — 에셋을 기다리지 않는다

**1~5번 묶음은 프리미티브로 개발하고, 에셋은 작업 6.6 에서 끼워 넣는다.**

- 코인 = `Cylinder`, 망치 = 길쭉한 `Cube`
- 타격 대상 4종은 모양과 색으로 구분한다 — 일반 `Cube` / 거치 `Cylinder` / 고속 `Sphere` /
  회복 `Capsule`, 머티리얼 4개. **회복형을 빠뜨리지 않는다** — 부수면 스태미나를 돌려주는
  대상이라 한눈에 구분돼야 한다 (GDD 4절)
- 이 상태로 **작업 2.6 완주 빌드까지 간다.** 박스가 돌아다니고 커서를 올리면 코인이 튀어나오면 게임은 완성된 것이다. 예쁜 건 나중 문제다

교체가 재작업이 되지 않으려면 프리팹 구조를 지금 정해야 한다.

### 프리팹 구조 규칙 (필수)

```
Piggy_Normal (프리팹 루트)
├─ [로직]  Collider, PiggyController, IHittable 구현     ← 코어 플레이 담당 소유
└─ Visual  (빈 GameObject)                                ← UI·연출 담당 소유
   └─ Mesh  ← 그레이박스 Cube → 나중에 VARCO 3D 모델로 교체
```

- **로직 컴포넌트는 루트에만 붙인다.** 메시 오브젝트에 직접 붙이면 교체할 때 같이 날아간다.
- 콜라이더도 루트에 둔다. 모델이 바뀌어도 판정 크기는 그대로여야 밸런스가 유지된다.
- 교체는 `Visual` 아래 자식을 갈아끼우는 것으로 끝나야 한다. 이 조건이 지켜지면 **에셋 교체가 코어 담당자의 작업을 건드리지 않는다.**
- 스크립트에서 메시를 참조할 일이 있으면 `Visual` 트랜스폼까지만 참조한다 (스쿼시&스트레치는 `Visual`을 스케일한다 — 루트를 스케일하면 콜라이더까지 커진다).

## 2. VARCO 3D 사용 규칙

### 먼저 확인할 것 (킥오프)

VARCO 3D 의 출력 사양을 팀에서 한 번 확인하고 아래를 채운다. 확인 전에는 에셋을 여러 개 만들지 않는다 — **기준 없이 10개 만들면 10개를 다시 만들어야 한다.**

- [ ] 내보내기 포맷 (`.glb` / `.fbx` / `.obj`) 및 Unity 임포트 시 이상 유무
- [ ] 폴리곤 수 조절 가능 여부 — 목표는 저금통 1체당 **1,000~2,000 삼각형**
- [ ] 텍스처 해상도 — 512×512 로 충분하다. 책상 위 작은 오브젝트라 2K는 낭비다
- [ ] 머티리얼이 URP 셰이더로 들어오는지 (Built-in 셰이더로 들어오면 분홍색으로 보인다 → `Edit > Rendering > Materials > Convert...` 로 일괄 변환)
- [ ] 생성물의 이용 조건 — 수업/포트폴리오/공개 배포 각각 가능한지 ([THIRD_PARTY.md](THIRD_PARTY.md)에 기록)

### 스케일 기준

**저금통 높이를 0.4 유닛으로 통일한다.** 기준은 미터가 아니라 **확정된 카메라 구도**다.

이 값은 실물 크기가 아니라 화면에서 차지하는 비율로 정했다. 확정된 카메라(작업 1.1.3 —
Perspective, FOV 45, 높이 5.64, 내려보기 46.9°)에서 책상 평면의 보이는 세로 범위는 약 6.4 유닛이고,
`DeskPlane_Greybox` 자체가 6×6 유닛이다. 여기서 0.4 유닛은 **화면 세로의 약 6%** 다.

> **이전 기준(0.12 유닛 = 12cm)은 쓰지 않는다.** 같은 카메라에서 화면 세로의 1.9%,
> 1080p 기준 세로 20픽셀밖에 안 돼 조준이 성립하지 않는다. 카메라가 확정되기 전에 적힌 값이라
> 구도를 반영하지 못했다. 1유닛=1미터로 읽으면 책상이 6m가 되므로 **미터 환산은 하지 않는다.**

모델마다 크기가 제각각이면 카메라와 이동 속도, 콜라이더 크기가 전부 어긋난다. VARCO 3D 출력이 다른 크기로 나오면 **프리팹에서 스케일을 조정하지 말고 임포트 설정의 Scale Factor 에서 맞춘다** — 프리팹 스케일을 건드리면 자식 파편의 물리 거동이 같이 틀어진다.

**피격 판정 반경은 이 크기에서 재지 않는다.** 모델이 바뀌어도 판정이 그대로여야 밸런스가 유지되므로,
반경은 프리팹 루트에 고정값으로 두고 `economy.csv` 의 `hit_radius_bonus` 만 곱한다 (1절).

### 만들 목록 (우선순위 순)

| 순위 | 에셋 | 용도 | 비고 |
|---|---|---|---|
| 1 | 저금통 일반형 | 가장 많이 보임 | 이것만 나와도 화면이 산다 |
| 2 | 저금통 파편 조각 | 파괴 연출 | 8~12조각. 원본을 쪼갠 형태 |
| 3 | 코인 | 획득 연출 | 단순 원기둥으로 대체 가능 |
| 4 | 저금통 거치형 / 고속형 / **회복형** | 종류 구분 | 색·크기 변형으로 먼저 때워도 됨. 회복형은 **부수면 스태미나를 돌려주는 핵심 대상**이라 눈에 띄게 구분돼야 한다 |
| 5 | 망치 | 플레이어 표현 | 화면 하단에 항상 보임 |
| 6 | 책상·배경 소품 | 분위기 | 없어도 게임은 성립. 시간 남으면 |

**4순위부터는 없어도 작업 7.3 배포 후보 빌드가 나온다.** 일정이 밀리면 여기부터 자른다.

## 3. 파손 표현

원작은 타격할수록 저금통에 금이 누적되다가 파괴된다. 모델을 단계별로 여러 개 만들 필요는 없다.

- **크랙 텍스처를 머티리얼에 얹고 HP 비율에 따라 알파를 올린다.** 모델은 하나면 된다.
- 파괴 순간에만 원본을 끄고 파편 프리팹을 켠다. 파편에는 리지드바디를 붙여 물리로 흩어지게 둔다.
- 파편은 3초 뒤 사라지게 한다 — 바닥에 계속 쌓이면 드로우콜이 늘고 화면이 지저분해진다.

## 4. 성능 예산

[ARCHITECTURE.md](ARCHITECTURE.md) 5절의 예산을 3D 기준으로 구체화한 것이다.

- 드로우콜 **200 이하**, 화면 내 삼각형 **15만 이하**
- **그림자를 드리우는 것은 타격 대상만.** 파편·코인은 `Cast Shadows = Off` — 동시 50개가 그림자를 드리우면 그것만으로 프레임이 무너진다
- 파편과 코인은 오브젝트 풀에서 꺼내 쓴다 ([PATTERNS.md](PATTERNS.md) 7절)
- 라이트는 **Directional 1개 + 앰비언트**로 시작한다. 포인트 라이트를 저금통마다 붙이지 않는다
- 작업 7.1 프로파일링에서 위 수치를 실측한다. "느낌상 괜찮다"로 판단하지 않는다

## 5. 커밋 규칙

- 3D 모델·텍스처는 바이너리라 Git 이력에 누적된다. **같은 파일을 여러 번 덮어쓰며 커밋하지 않는다** — 최종본이 나온 뒤 한 번에 올린다
- 파일이 커지면 `.gitattributes` 의 LFS 섹션 주석을 해제한다 (전원 `git-lfs` 설치 필요)
- 에셋을 추가한 PR에서 [THIRD_PARTY.md](THIRD_PARTY.md) 표를 같이 갱신한다
